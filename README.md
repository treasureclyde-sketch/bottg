# 💈 Telegram-бот онлайн-записи для барбершопа / салона

Production-ready бот для онлайн-записи клиентов в **один** барбершоп или бьюти-салон.
Ведёт запись по свободным слотам, рассылает напоминания (чтобы снизить неявки), а вся
админка живёт прямо внутри Telegram — отдельной веб-панели нет.

Один бот = один салон. Чтобы запустить бота для следующего клиента, достаточно
скопировать проект, поменять `.env` и пересоздать демо-данные.

---

## Возможности

**Клиент**
- `/start` — приветствие с названием салона и главное меню.
- Запись: (филиал, если их 2+) → услуга → мастер → дата → время → имя → телефон → подтверждение.
- **Филиалы** (для сети с несколькими адресами): клиент сначала выбирает филиал, дальше
  показываются только мастера этого филиала. Если филиал один или их нет — шаг пропускается.
- «Мои записи» — список будущих визитов, **отмена** и **перенос**.
- «Наши работы» — портфолио-альбом с фото примеров (раздел появляется, только если в папке `works/` есть фото).
- Автоматические напоминания: накануне визита и за ~2 часа.

**Администратор** (определяется по Telegram ID в `.env`)
- Записи на сегодня / завтра / неделю + отмена любой записи (клиент получает уведомление).
- Услуги: добавить, изменить (название/цена/длительность), скрыть/показать, удалить.
- Мастера: добавить/переименовать, скрыть/показать, удалить; расписание по дням недели;
  **привязать Telegram-аккаунт мастера** (чтобы он видел свои записи); **назначить филиал**.
- Филиалы: добавить/изменить (название, адрес), скрыть/показать, удалить — раздел «📍 Филиалы».
- Блокировки: отметить день/промежуток как недоступный (отпуск, болезнь, перерыв) — для
  конкретного мастера или для всего салона.
- Уведомления на каждую новую запись и на каждую отмену клиентом.

**Мастер** (барбер; определяется по привязанному Telegram ID)
- Кнопка «👤 Мои записи (мастер)» — видит **только свои** предстоящие записи (время,
  услуга, имя и телефон клиента).
- Может отменить свою запись — клиент и владелец салона получают уведомление.
- **Свой профиль** — барбер сам редактирует имя, описание/специализацию и фото
  (раздел «✏️ Мой профиль» в кабинете). Услуги/расписание не меняет — это у владельца.
- При выборе мастера клиент видит **карточки**: фото + имя + описание. Это решает
  проблему одинаковых имён (два «Алексея» различаются по описанию/фото). Запись всегда
  привязана к ID мастера, а не к имени, — перепутать барбера нельзя.
- **Вход по ссылке-приглашению** (рекомендуется): владелец в админке открывает мастера →
  «🪄 Ссылка для входа» → бот даёт одноразовую ссылку `t.me/<bot>?start=join_…`. Владелец
  пересылает её барберу, тот **тапает один раз** — аккаунт привязан, без пароля и без
  @userinfobot. Один аккаунт = один мастер; повторная привязка снимает старую.
- Альтернатива: «🔗 Telegram ID» — владелец вводит ID мастера вручную (отвязать — `-`).

> Почему не логин/пароль: Telegram-аккаунт уже подтверждён телефоном и не подделывается,
> поэтому привязка аккаунта надёжнее пароля (пароль виден в истории чата, его можно
> передать, и его пришлось бы сбрасывать). Ссылка-приглашение даёт ту же простоту
> «выдал доступ», но без этих проблем.

## Технологии

- **Python 3.11+** (разрабатывалось и проверялось на 3.12), весь код асинхронный, с type hints.
- **aiogram 3.x** — фреймворк бота, сценарий записи на FSM.
- **SQLAlchemy 2.0 (async) + aiosqlite** — БД в одном файле SQLite.
- **APScheduler** — планировщик напоминаний.
- **pydantic-settings** — конфиг из `.env`.
- Режим работы — **long-polling** (без webhook), чтобы легко поднимать на дешёвом VPS.
- Все даты/время — **timezone-aware**; таймзона берётся из конфига.
- Все тексты для пользователя — на русском, вынесены в `texts.py`.

## Быстрый старт (локально)

1. **Получить токен бота.** Откройте в Telegram [@BotFather](https://t.me/BotFather) →
   `/newbot` → задайте имя и username → получите `BOT_TOKEN`.

2. **Узнать свой Telegram ID.** Напишите [@userinfobot](https://t.me/userinfobot) — он пришлёт
   ваш числовой `id`. Это значение пойдёт в `ADMIN_IDS`.

3. **Установить зависимости** (нужен Python 3.11+):

   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   ```

4. **Настроить `.env`:**

   ```bash
   cp .env.example .env
   # откройте .env и впишите как минимум BOT_TOKEN и ADMIN_IDS
   ```

5. **Запустить:**

   ```bash
   python bot.py
   ```

   При первом запуске автоматически создаётся файл БД (`bot.db`) и засеваются демо-данные:
   один мастер «Алексей» (пн–пт 10:00–20:00, сб 11:00–18:00, вс выходной) и 4 услуги
   (мужская стрижка, стрижка + борода, оформление бороды, детская стрижка).

6. Откройте бота в Telegram, отправьте `/start`. Админам доступна кнопка «⚙️ Админ-панель»
   и команда `/admin`.

> Если `BOT_TOKEN` или `ADMIN_IDS` не заполнены — бот не запустится и подскажет, что поправить.
> Если токен неверный — выведет понятное сообщение про @BotFather.

## Конфигурация (`.env`)

| Переменная                    | По умолчанию     | Назначение |
|-------------------------------|------------------|------------|
| `BOT_TOKEN`                    | —                | **Обязательно.** Токен от @BotFather. |
| `ADMIN_IDS`                    | —                | **Обязательно.** Telegram ID админов через запятую: `123,456`. |
| `BUSINESS_NAME`               | `Барбершоп`      | Название салона (в текстах). |
| `BUSINESS_ADDRESS`            | пусто            | Адрес (в контактах и подтверждениях). |
| `BUSINESS_PHONE`              | пусто            | Телефон салона (в контактах). |
| `TIMEZONE`                    | `Europe/Moscow`  | Таймзона для всех дат/времени. |
| `SLOT_STEP_MIN`               | `30`             | Шаг сетки слотов в минутах. |
| `BOOKING_HORIZON_DAYS`        | `14`             | На сколько дней вперёд можно записаться. |
| `BOOKING_BUFFER_MIN`          | `30`             | На сегодня не показывать слоты ближе, чем через N минут. |
| `REMINDER_DAY_BEFORE_HOUR`    | `20`             | Час (0–23), когда слать напоминание накануне. |
| `REMINDER_2H_ENABLED`         | `true`           | Включить напоминание за ~2 часа. |
| `REMINDER_CHECK_INTERVAL_MIN` | `5`              | Как часто планировщик проверяет брони. |
| `DB_PATH`                     | `bot.db`         | Путь к файлу SQLite. |
| `SUBSCRIPTION_UNTIL`          | пусто            | Дата `ГГГГ-ММ-ДД`, до которой оплачена подписка. Пусто = бессрочно. Fallback, если биллинг недоступен. |
| `CLIENT_SLUG`                 | пусто            | Идентификатор салона в центральном биллинге (включает чтение `billing.db`). |
| `BILLING_DB_PATH`             | пусто            | Путь к общей `billing.db`. Пусто = биллинг выключен, берётся `SUBSCRIPTION_UNTIL`. |
| `PROVIDER_CONTACT`            | пусто            | Твой контакт (напр. `@username`) — показывается админу салона при неоплате. |
| `WORKS_DIR`                   | `works`          | Папка с фото для раздела «Наши работы». Нет папки/пусто — раздел скрыт. |

Биллинг-бот провайдера настраивается отдельно — см. `.env.billing.example`
(`BILLING_BOT_TOKEN`, `BILLING_ADMIN_IDS`, `BILLING_DB_PATH`, `ANNUAL_PRICE`).

Тарифы (помесячно 500 ₽ / год 5000 ₽ — «2 месяца в подарок») — это договорённость с
салоном; бот деньги не принимает. Годовая = кнопка «🗓 +1 год» (`ANNUAL_PRICE` задаёт
лишь подпись). Продление на любой срок — датовое, отдельного «плана» в БД нет.

## Как работает логика слотов

Для пары **мастер + услуга** на конкретную дату:

1. берутся рабочие интервалы мастера на этот день недели (`master_schedule`);
2. интервал нарезается шагом `SLOT_STEP_MIN`;
3. слот доступен, только если отрезок `[слот; слот + длительность услуги]` целиком влезает
   в рабочее время и **не пересекается** ни с активными бронями этого мастера, ни с
   блокировками (персональными или общесалонными);
4. слоты в прошлом не показываются (для сегодняшней даты учитывается `now + BOOKING_BUFFER_MIN`);
5. в выборе дат показываются только дни, где есть хотя бы один свободный слот.

Перед самим сохранением брони слот проверяется ещё раз — защита от ситуации, когда два
клиента одновременно выбрали одно время.

## Напоминания и идемпотентность

Одна периодическая задача (раз в `REMINDER_CHECK_INTERVAL_MIN` минут) проверяет активные
брони и шлёт:

- **накануне** — в `REMINDER_DAY_BEFORE_HOUR` дня перед визитом;
- **за ~2 часа** — если `REMINDER_2H_ENABLED=true`.

Факт отправки сохраняется в БД (`reminder_day_sent`, `reminder_2h_sent`), поэтому
напоминание **не дублируется** даже при перезапуске бота.

---

## Принятые решения по умолчанию

Там, где задача допускала варианты, выбрано следующее (меняется в коде/`.env`):

- **Хранение времени.** В SQLite datetime физически хранятся в UTC, на чтении возвращаются
  timezone-aware; для пользователя переводятся в `TIMEZONE`. Так время всегда корректно.
- **Новый мастер** создаётся с пустым расписанием (все дни — выходные). Пока админ не задаст
  рабочие часы, на этого мастера нельзя записаться. Это исключает «случайную» доступность.
- **Перенос записи** = отмена старой брони + создание новой. Услуга и мастер сохраняются —
  меняются только дата и время. Админу при переносе приходит уведомление о **новой** записи
  (отдельного уведомления об отмене не шлётся, чтобы не создавать шум).
- **Удаление услуги/мастера** — «жёсткое». Чтобы сохранить историю и не ломать прошлые записи,
  для временного снятия с показа используйте **«Скрыть/Показать»**, а не «Удалить».
- **Напоминание накануне** отправляется только если визит приходится на следующий
  календарный день (для корректной формулировки «завтра»). Если бот был выключен и пропустил
  момент отправки, накануне-напоминание не дублируется задним числом — но за 2 часа всё равно
  придёт.
- **Имя клиента** предзаполняется из профиля Telegram; его можно подтвердить или ввести своё.
- **Телефон** — через кнопку «Отправить номер» (`request_contact`) либо вручную (валидируется).
- В выборе показываются только активные услуги/мастера; неактивные видны лишь админу.

## Деплой на дешёвый VPS (Ubuntu) + автозапуск через systemd

### 1. Подготовка сервера

```bash
sudo apt update
sudo apt install -y python3 python3-venv python3-pip git
```

### 2. Загрузка проекта и зависимостей

```bash
# например, в /opt/booking-bot
sudo mkdir -p /opt/booking-bot
sudo chown $USER:$USER /opt/booking-bot
cd /opt/booking-bot

# скопируйте сюда файлы проекта (git clone / scp / rsync), затем:
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
nano .env          # впишите BOT_TOKEN, ADMIN_IDS и реквизиты салона
```

Проверьте разовый запуск: `python bot.py` (Ctrl+C для остановки).

### 3. systemd-юнит для автозапуска

Создайте файл `/etc/systemd/system/booking-bot.service`:

```ini
[Unit]
Description=Telegram booking bot
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
# при необходимости укажите своего пользователя вместо ubuntu
User=ubuntu
WorkingDirectory=/opt/booking-bot
ExecStart=/opt/booking-bot/.venv/bin/python /opt/booking-bot/bot.py
Restart=always
RestartSec=5
# EnvironmentFile не обязателен — конфиг и так читается из .env в WorkingDirectory
# EnvironmentFile=/opt/booking-bot/.env

[Install]
WantedBy=multi-user.target
```

Включите и запустите:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now booking-bot
sudo systemctl status booking-bot      # проверить, что active (running)
journalctl -u booking-bot -f           # смотреть логи в реальном времени
```

Теперь бот сам поднимется после перезагрузки сервера и перезапустится при падении.

### 4. Обновление

```bash
cd /opt/booking-bot
# обновите файлы проекта
sudo systemctl restart booking-bot
```

## Много ботов на одном сервере (SaaS-конвейер)

Один сервер может крутить десятки таких ботов: каждый бот — отдельный процесс со
своим `.env` и своей БД. Код при этом **общий** — обновил репозиторий, перезапустил
ботов, и все получили апдейт.

### Раскладка на сервере

```
/opt/booking-bot/        # общий код этого репозитория + .venv (один на всех)
/opt/bots/
├── billing.db           # общая БД подписок (читают салонные боты, пишет биллинг-бот)
├── billing/.env         # конфиг биллинг-бота провайдера
├── borodach/            # данные клиента: .env, bot.db, works/
├── topgun/
└── ...
```

### Подписочная модель (стоп-кран по оплате)

Когда подписка истекает, бот **сам приостанавливается**: клиентам показывает «запись
временно недоступна» (+ телефон салона), админу салона — «продлите оплату» с твоим
контактом из `PROVIDER_CONTACT`. Вырубать процесс руками не нужно.

Источник даты «оплачено до» — на выбор:

- **Простой режим:** `SUBSCRIPTION_UNTIL=ГГГГ-ММ-ДД` прямо в `.env` бота. Продлил →
  поменял дату → `systemctl restart bot@<slug>`.
- **Центральный биллинг (рекомендуется для конвейера):** дату хранит общая `billing.db`,
  а бот читает её **на лету** — продление подхватывается **без рестарта** (в пределах
  кэша ≤ 60 c). Включается заданием `CLIENT_SLUG` + `BILLING_DB_PATH` в `.env` бота.

Сами деньги (например, 500 ₽/мес) бот не принимает — это перевод тебе вне бота;
в боте только «вкл/выкл по дате».

### Биллинг-бот провайдера (управление подписками в один тап)

Отдельный бот (твой, со своим токеном) для управления подписками **всех** салонов из
одного места. Работает поверх общей `billing.db`.

- `/clients` — список всех салонов со статусом (🟢 оплачено до DD.MM / 🟠 скоро истекает /
  🔴 просрочено N дней).
- Тап по салону → «➕ 30 дней» / «➕ 7 дней» / «🗓 +1 год» / «⏸ Приостановить» / «🗑 Удалить».
- `/add <slug> <дней> [название]` — зарегистрировать/продлить вручную (годовая: `/add slug 365`).
- Раз в день (10:00) шлёт тебе дайджест: у кого истекает в ближайшие 3 дня или уже просрочено.

Продление через биллинг-бот сразу отражается на салонном боте — рестарт не нужен.

**Принцип отказоустойчивости (fail-open):** если `billing.db` недоступна или клиента в
ней нет, салонный бот **не глушит всех** — он откатывается на статичный
`SUBSCRIPTION_UNTIL` из своего `.env` и пишет предупреждение в лог. Чтобы реально
приостановить салон через биллинг, у него должна быть строка в `billing.db` (её создаёт
`new_client.py` автоматически, если в брифе задан `billing_db_path`).

Запуск биллинг-бота:

```bash
# в папке /opt/bots/billing/ создайте .env из .env.billing.example
sudo cp deploy/billing-bot.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now billing-bot
```

> Сейчас оплата подтверждается тобой в один тап (эквайринг не нужен). Когда подключишь
> ЮKassa/Telegram Payments — приём денег встанет поверх этой же `billing.db`: платёж
> просто будет двигать `paid_until` автоматически, а салонные боты уже умеют это читать.

### Развёртывание нового клиента — 1 команда

1. Создай **нового** бота у @BotFather → получи `BOT_TOKEN` (1 минута).
2. Возьми у клиента его Telegram ID (через @userinfobot) и данные салона.
3. Заполни бриф по образцу [`briefs/example.json`](briefs/example.json) — токен, ID,
   услуги, мастера с графиком, дату подписки. Для сети добавь `branches` (название+адрес),
   а у мастера укажи `branch` (имя филиала) и `description` (уровень/специализация).
   Реальный пример сети с двумя филиалами — [`briefs/gagarin.json`](briefs/gagarin.json).
4. Разверни:

   ```bash
   python new_client.py briefs/<client>.json /opt/bots
   ```

   Скрипт создаст `/opt/bots/<slug>/` с `.env`, засеет `bot.db` реальными услугами и
   мастерами клиента и создаст папку `works/` для фото.

5. (Опционально) Положи фото примеров работ в `/opt/bots/<slug>/works/` — появится
   раздел «Наши работы».
6. Поставь шаблонный systemd-юнит (один раз на сервер) и запусти клиента:

   ```bash
   sudo cp deploy/bot@.service /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemctl enable --now bot@<slug>     # <slug> = поле slug из брифа
   sudo systemctl status bot@<slug>
   journalctl -u bot@<slug> -f
   ```

Дальше клиент всё донастраивает сам в Telegram через «⚙️ Админ-панель».

### Управление ботами

```bash
sudo systemctl stop bot@<slug>       # приостановить
sudo systemctl restart bot@<slug>    # после правки .env
sudo systemctl disable --now bot@<slug>   # отключить совсем
systemctl list-units 'bot@*'         # какие боты запущены
```

### Бэкапы (сделай до первого платящего клиента)

Потеря `bot.db` = потерянные записи салона. Простейший nightly-бэкап через cron:

```bash
# crontab -e
0 4 * * *  tar czf /opt/backups/bots-$(date +\%F).tgz /opt/bots/*/bot.db && find /opt/backups -name 'bots-*.tgz' -mtime +14 -delete
```

## Запуск одиночного бота под нового клиента (без конвейера)

Если разворачиваешь по-простому, в одном каталоге:

1. Скопируй проект в новый каталог, создай нового бота у @BotFather.
2. Заполни `.env`: `BOT_TOKEN`, `ADMIN_IDS`, `BUSINESS_NAME`, адрес, телефон, таймзону.
3. Удали `bot.db` и запусти бота — демо-услуги и мастер засеются заново; дальше всё
   настраивается через «⚙️ Админ-панель». Демо-набор в `db/seed.py` тоже можно
   поправить под типового клиента.
